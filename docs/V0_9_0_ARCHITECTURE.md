# v0.9.0 architecture and compatibility work

Status: implementation in progress; v0.8.3 remains the production/recovery baseline. The new account path is connected only behind `VITE_ACCOUNT_CLOUD_V2=preview`, OFF by default. No production migration, API call or deployment is authorized. A successful local test does not approve production conversion.

## Audited baseline (2026-10-28, Hong Kong)

- Committed baseline 8769046 on `feature/v0.9.0`, package 0.8.3. Vite/React/TypeScript, npm lockfile, Cloudflare Workers static assets; CSP restricts requests to the configured Supabase HTTPS origin.
- AuthApp verifies getUser, confirmed/non-anonymous identity and session expiry, then opens a separate Account Vault. Invitation-only OTP uses shouldCreateUser=false. Guest owns tco-logbook-demo-v0.1; signing in never transfers it.
- Account local envelope v1 uses AES-256-GCM, fresh 12-byte IV, 16-byte salt, PBKDF2-HMAC-SHA256/600000 iterations and user-bound AAD. Unwrapped keys and passphrases remain in memory. Internal vaultFormat 2 carries durable sync baselines/conflicts/cursor with the database.
- tco_sync.accounts stores immutable wrapped cloud keys. tco_sync.records stores per-record ciphertext and tombstones. Three SECURITY DEFINER RPCs are owned by the restricted NOLOGIN/NOINHERIT/NOBYPASSRLS executor; forced ownership RLS uses the private JWT request helper. Revisions are account-wide compare-and-swap.
- Operational database schema stays 1: aircraft, duties, journals and settings(language/privacy). Disruptions live inside aircraft; journals and disruptions reference stable IDs. No separate calendar collection. Pending is a date-derived Draft display state, not a persisted status.
- Operational date is distinct from createdAt/updatedAt; gate timestamps retain their original bytes and HKT semantics. Full Turnaround remains one assignment with independent legs. Incomplete Drafts remain valid; Confirm requirements depend on enabled fields.
- Sync enumerates one privacy/settings record even with zero aircraft. Language is device-local. New Guest/Account preferences have six enabled toggles; saved false values are authoritative.
- Existing retry/reconcile is local-before-remote, versioned, consent-gated, fenced on lock/account switch, and preserves both conflict versions. Service Worker caches only the app shell, not APIs/records/tokens.
- Existing backup validator is stricter than permissive historical local loading. Do not silently normalize or delete a legacy record that fails new import validation; stop and retain its original bytes.

## Storage decision

New storage will be a separate server-readable account model protected by TLS, per-account RLS and server-verified identity. It is NOT end-to-end encrypted. The host/database administrator can access record contents. Browser-local account cache will also need an explicit documented device security model; encrypting it with a key stored alongside it is not a substitute for a user-held secret.

An account-managed encryption key served back after OTP would not protect records from the provider serving that key, while adding recovery/fencing complexity. It is not represented as E2EE.

New and legacy tables must coexist. Legacy encryption/restore remains available until conversion has been verified. New mode must not be enabled merely by updating frontend version strings.

## Database design and guardrails

- A new private account schema has an authoritative workspace/onboarding row, per-record revisions/tombstones, idempotent operation receipts and immutable prior versions for replacement recovery.
- New-account detection must use workspace/onboarding state AND legacy-account existence, never aircraft count. A legacy privacy-only account is established.
- Ownership comes only from server-validated JWT claims via the reviewed private helper; never an RPC owner argument. Anonymous auth remains rejected.
- RPCs use a narrowly scoped non-bypass owner, fixed empty search_path, explicit authenticated EXECUTE, forced RLS, account row locking and bounded payloads. Browser roles have no direct private-table DML.
- Every transaction validates shape, IDs, collection identity, revision, links and total bounds. A reused operation ID with a different request must fail. Recovery versions and migration receipts share ownership RLS.
- Legacy conversion must fence old-client writes server-side and lock the legacy account revision before committing. Old ciphertext/key envelopes stay unchanged/readable for recovery. A newer legacy revision invalidates conversion review.
- Manual archival is the approved retention policy. The owner must download and reread the exact archive bytes, then explicitly approve. Current rows and tombstones stay; old history and non-initial receipts are archived only after the approved snapshot. Expired offline devices are fenced by a replay floor and require a fresh review. No automatic pruning. Ordinary logout/disable never deletes data. Auth-user deletion and provider backup retention limitations remain separate risks.
- The rollout is behind the OFF-by-default build flag `VITE_ACCOUNT_CLOUD_V2=preview`. Missing migration fails closed with a setup error; never create an empty replacement over existing data.

## Legacy transition

The preview Account entry now offers an explicit Legacy conversion review beside the original read-only recovery path. Local-only, cloud-only, identical and divergent sources are inspected without enabling the old SyncEngine or writing the old Vault. Local and cloud passphrases may differ. Settings-only encrypted accounts remain established accounts, never candidates for an empty replacement.

Every differing collection-qualified identity is shown individually, with field differences and explicit Cloud/Local/Manual choices. Retained local sync conflict baselines are separately selectable and included in the backup. The existing Aircraft/Duty/Journal editors stage manual results without persistence or upload; privacy has per-field controls. Stable IDs are preserved, original cloud tombstones remain covered by the manifest, and unsent local deletions represented in the old sync baseline remain reviewable tombstones. A missing source is not an implicit deletion. Incomplete choices, invalid historical records or inconsistent Duty/Aircraft/Journal/disruption references block conversion until repaired through a reviewed source. Language remains a device preference; privacy is part of the synchronized records.

Before submission, the user accepts that the new storage is server-readable, NOT E2EE, and uses a plaintext cache/recovery plan. The independent downloaded legacy backup includes both full plaintext sources, retained sync conflict alternatives, untouched local encrypted bytes, the cloud key envelope and ciphertext. The actual selected file is reread and checked against its exact SHA-256 digest. Final counts, privacy settings and replacement/deletion choices require a separate confirmation. No passphrase or unwrapped key is saved in the new plan.

`tco-legacy-conversion-v1:<userId>` stores the approved exact request and original sources only after consent, backup verification and final confirmation. This plaintext plan remains available after completion and must be protected like an unencrypted backup. Before approval, postponing/reloading safely restarts review and unlock; original data is unchanged. After approval, reload restores the same operation UUID, manifest and payload. Account-entry and both account-bound transports fence authentication changes; conversion and original-Vault Web Locks serialize local attempts and prevent supported old-client writes during source checks. The server checks the legacy revision and exact initialization receipt; a lost response never creates another conversion UUID. Independent full downloads are compared with the entire proposed dataset before the existing verification RPC is called, and an additional active-state download must pass before completion or opening the new workspace. Subsequent normal new-Account use requires no Vault passphrase.

Approved plans can be exported and explicitly restored on the same authenticated account, with a fresh plaintext-storage acknowledgement; restore alone does not upload. A superseded plan is retained under an operation-qualified recovery key. An unknown request may only be superseded when a newer authoritative legacy revision proves its old initialization can no longer succeed; an already established new workspace must instead resume exact verification. This avoids abandoning an upload that may still commit.

Fail-closed limits: no missing/deleted source key is replaced, incompatible/corrupt encrypted data is never skipped, and a graph that cannot be reconciled remains blocked with both sources intact. Losing both the approved plan and its exported recovery copy can prevent exact recovery of an already submitted conversion; never initialize a different plan over it. A destination changed by another device after activation but before local completion is retained and requires reviewed History/forward recovery rather than a second import. A plan restored elsewhere before its first upload cannot verify a missing original local source; resume on the original device. Empty legacy cloud keys without a usable settings record are not converted into invented default records. Browser quota failures stop before upload when saving the plan fails. There is no automatic cleanup of old ciphertext, plans, receipts or history.

1. Detect both local encrypted Vault and authoritative legacy cloud account, including settings-only accounts.
2. Offer postpone/use legacy. Unlock using original local/cloud passphrases only for migration/recovery.
3. Reconcile legacy sources explicitly, verify independent JSON backup and show source/destination/security-model disclosure.
4. Persist a stable migration ID and complete reviewed plan locally before sending. Preserve original vault bytes.
5. Atomically check legacy revision, fence old writes, copy reviewed data into the new model with recovery receipt. Do not replace old keys.
6. Pull and validate the committed destination before reporting completion. Interrupted/unknown acknowledgement retries use the same receipt, not a new import.
7. Rollback frontend must not resume legacy writes against migrated accounts. Recovery is reviewed export/import or forward repair, never deleting the new workspace.

## Guest merge contract

Current preview UI opens after a saved Guest workspace is detected or from Account Settings. It requires planning consent before matching, shows individual candidates and differences (including privacy-hidden values), offers only Keep Cloud, Keep Local and Manual Edit as primary choices, and stages edits through the existing Aircraft/Duty/Journal editors. Eligible exact/likely one-to-one matches alone support bulk Cloud/Local selection. Final queueing requires a separate confirmation and additional high-risk approval. The original Guest key is not written. A stale review cannot submit; its prior plan must be downloaded and reread before replacement. An unsubmitted review can be cancelled only after downloading and rereading its complete plan; queued operations are never labelled cancelled merely because a dialog closes. Ordinary same-record conflicts require a separate verified recovery file and explicit per-record Cloud/Local choice. The fourth-pass lifecycle below now handles clean queued, uncertain, stale and expired submissions. The mixed-queue section below now handles additional Account edits through a separately approved, durable reconciliation.

## Guest submission lifecycle (Fourth Pass A, 2026-10-29 Hong Kong)

The durable operation retains its original UUID, expected revision and exact record array. `guestDelivery` is local protocol metadata, excluded from the server request hash. The sync Web Lock and cache compare-and-swap serialize first transmission and cancellation across current-version tabs. A write-ahead `unknown` marker is stored before invoking the upload transport. Old caches without a marker are conservatively unknown. Ordinary Account record edits are refused while a Guest submission or renewed recovery review is unresolved.

| State                                  | Evidence                                                                     | Safe action                                                                                                            |
| -------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Review, not queued                     | No durable upload operation                                                  | Save/reread plan, cancel or resume review                                                                              |
| Queued, not transmitted                | Durable queued marker; first push has not started                            | Save/reread recovery file, cancel under sync lock; no remote rollback                                                  |
| Transmission started / response lost   | Durable unknown marker                                                       | Owner-scoped receipt lookup; a missing receipt remains uncertain                                                       |
| Original absent, user chooses retry    | Exact payload and ID retained; same Guest source and expected Cloud revision | Explicit exact idempotent retry, never a new operation                                                                 |
| Server rejected or destination changed | CAS refusal or authoritative preflight differs                               | Save/reread recovery, retire original under account lock, download current Cloud, redo complete review                 |
| Server committed                       | Exact-payload receipt, account/workspace/revision checked                    | Independent full read, preserve any later Cloud edits, mark original transfer verified; never import again             |
| Replay floor expired                   | Original receipt may have been manually archived                             | Save/reread recovery, full Cloud read, complete new Guest review; never claim cancellation or replay the old operation |
| Account/session changed                | Auth token binding, abort/epoch and adapter identity guards                  | Stop requests; retain that account's pending cache for its next verified sign-in                                       |

The additive `202610290001_guest_merge_recovery.sql` migration supports both the earlier staged database and fresh sequential installs. Its `tco_account_merge_outcome` RPC uses the same restricted executor, forced owner RLS, authenticated JWT identity and exact Guest request hash as push. It accepts no owner ID. Inspection changes no records or receipts. With explicit recovery approval, retirement and push contend on the same account row lock: either an existing committed receipt wins, or a retired receipt fences all delayed copies of that operation. Reusing an ID with different bytes fails. It never deletes current records to simulate cancellation.

Retired receipt `revision` records the original expected revision; committed receipt `revision` records the committed revision. Manual archives retain retirement fences at the exact replay floor. A later approved archive may remove a fence only once the request's expected revision is below the floor, where push rejects it regardless of missing receipt. No background pruning is introduced. Receipt capacity failures leave current records unchanged and the original local queue intact.

Renewed review preserves the original plan, pending database and operation in `AccountRecovery`, plus the independently reread recovery file. Only a successful server retirement or replay-floor result enables `guestReady`. Existing expired-device review alone cannot authorize a new Guest upload. The latest actual Guest bytes and full authoritative Cloud snapshot form a new plan with a new UUID, unresolved candidates and empty final approval; Confirmation 1, Confirmation 2 and high-risk approval are required again. No old decisions are silently rebased. Guest storage is never written.

## Mixed-queue reconciliation (2026-10-29 Hong Kong)

The previous `merge-local-edits` blocker is replaced with a durable, separately approved Account-edit review. The actual old format has one durable `operation` plus the latest database; it does not store a separate UUID or full chronology for every unsubmitted edit. Two valid old states are supported: the durable operation is still the Guest upload, with later dirty values in the database; or the Guest acknowledgement advanced the baseline and the durable operation now represents a later Account upload. Every available UUID, exact payload and final dirty value is preserved. No missing intermediate edit history is invented.

`MixedPlan.originalCache` retains the exact pre-reconciliation account-cache bytes with a SHA-256 digest, user/workspace binding, the original reviewed plan, all available operations, baselines and records. Decisions and rejected/superseded approvals are appended to local review history. Guest storage and encrypted Vaults are never written. Mixed recovery uses Account cache envelope version 2, so older preview code that only understands version 1 fails closed rather than ignoring the new write guards. Current code reads both versions; operational schema 1 and independent JSON backups are unchanged. A normal account without mixed recovery keeps its existing cache format.

| Stage                      | Preserved state and required action                                                                                                                                                                                         |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Awaiting Cloud             | Original operation outcome is resolved first; no later edit is sent. A proven-unsent cancellation removes only the Guest operation and retains all later data for review.                                                   |
| Retained Account operation | A separately recorded edit UUID is queried using `tco_account_edit_outcome`. Existing commits are acknowledged; uncommitted requests are retired under the account row lock. Unknown/network outcomes retain the operation. |
| Guest review               | Rejected/expired Guest transfers require complete current-source duplicate review, Confirmation 1, Confirmation 2 and any extra risk approval. Later Account edits remain blocked.                                          |
| Account review             | Each later edit has independent Keep Cloud, Keep Local or Manual Edit decisions. Local-only save or Guest approval cannot authorize this layer.                                                                             |
| Queued                     | A new separately approved Account operation is durably saved before transmission; exact UUID/payload retry survives reload and lost acknowledgements.                                                                       |
| Complete                   | Server acknowledgement and independent current snapshot verification are required. Recovery bytes and review history remain stored.                                                                                         |

The later edit intent is calculated in order: post-Guest baseline → recorded Account operation (if one exists) → final local state. This preserves a local reversion even when the final value equals the original merge baseline. Only paths changed by those layers are applied to the current Cloud candidate; unrelated newer Cloud fields are retained. Arrays remain explicit whole-value changes. Local deletions are tombstones and require complete graph validation alongside related edits.

Original Guest-created identities are mapped through the effective decisions of the newly verified Guest plan, using collection-qualified IDs. Pre-existing Account identities stay stable. Later Duty/Journal/Aircraft references follow those mappings. Missing/ambiguous mappings block Keep Local until the user reviews Guest dependencies, chooses an explicit existing target or manually repairs references. Changing a binding clears dependent decisions and preserves the previous review. Multiple writes to one target and invalid reference graphs are rejected atomically.

An unsent merge may be cancelled without discarding later edits. The user can review later edits without importing Guest data, but unbound Guest-derived identities cannot be uploaded through that path. Keep Cloud explicitly excludes only the selected unsent later edit; its original bytes remain recoverable. Dependent choices still have to form a valid complete graph. Manual Edit uses the existing record editors, and settings use explicit per-field controls.

Before applying the Account plan, the user downloads and rereads the current recovery file, resolves every item and gives a separate approval (plus deletion/concurrent-value approval where needed). Account/workspace, cache snapshot, source digest, full Cloud revision/content and complete graph are rechecked. A changed Cloud revision invalidates decisions, saves their history and starts a new review. A submitted Account operation is never silently rebased. An exact retry must confirm it, or CAS/replay-floor rejection plus a newer authoritative snapshot must fence future replay before renewed approval can create another UUID.

The additive `202610290002_mixed_queue_recovery.sql` adds only the Account-edit outcome RPC. It uses the same restricted executor, forced owner RLS, authenticated-only EXECUTE, fixed empty search path and exact request hash as Guest outcome verification, with a distinct `edit` purpose. There is no caller-supplied owner ID. Receipt checks send the exact queued payload to compute its hash; they do not write operational records. Both purposes share the existing atomic receipt retirement and manual-archive fence retention rules. All temporary migration role/schema permissions are removed.

Unsupported queue formats, corrupted source bytes, unavailable keys/credentials, storage quota failures or unresolved identity/reference choices remain Recovery Required with verified export available. The app never guesses missing IDs, drops a queue or claims cancellation/Sync success in those conditions. Hosted/physical-device acceptance remains a separate release gate for both recovery and Legacy conversion.

## Live History restoration

Account Settings can inspect up to 100 live prior versions per current record, compare field values and identify deletion. Restoration requires a separately downloaded and reread local recovery file, explicit review and an extra approval for replacing populated values or deletion state. The engine checks the account/workspace, server revision, fresh history response and local cache snapshot again, validates the complete record-reference graph, then writes a durable new `history-restore` operation using the account revision guard. A changed server revision or invalid graph blocks approval; a failed upload stays pending. SQL stores the displaced version in owner-only history. History older than the manual replay floor may be available only in the independently saved archive; this UI does not import archived history.

Guest source is never mutated. Only already persisted, validated Guest data is eligible; automatically displayed unsaved samples are not offered as the user's records.

Confirmation 1 identifies authenticated destination, Guest source/counts, and server-readable storage. It permits planning only. All duplicate decisions default unresolved. Final confirmation separately shows adds/skips/replacements/manual/separate records, settings effects and discarded nonempty values.

Canonical flight comparison strips leading numeric zeroes and normalizes prefix/suffix case without changing original strings. Date, independent legs, handling type, identity and other populated fields qualify matches. Conflicting supplied identities are never ignored. Cross-midnight matching uses actual/scheduled HKT leg instants rather than shifting operational dates blindly.

Connected candidate groups identify one-to-many/many-to-many cases; no greedy first-match winner. Bulk Keep Cloud/Keep Local applies only to isolated exact/likely matches. Partial, conflicting or ambiguous groups require individual review; bulk Manual Edit only marks work remaining.

A complete plan remaps copied stable IDs and all links, preserves destination preferences by default, validates the complete result, fingerprints both source and destination, and records immutable recovery versions before replacements. Idempotent retries must use the persisted plan/operation ID. Any destination/source change invalidates final approval. Completion means verified cloud acknowledgement, not closing UI or saving only the local plan.

## Test and rollout gates

Current capacity boundaries: the operational database validator allows 5 MiB, the separate plaintext account cache has a 16 MiB envelope guard (browser quota may be lower), and SQL limits current rows/tombstones to 5,000 / 8 MiB, history to 20,000 / 32 MiB, receipts to 20,000 and a per-record History read to 100. Capacity failures are atomic; approaching capacity calls for the manual verified-file archival procedure. These are application bounds, not a Supabase capacity guarantee.

Phases: (1) audit/design; (2) isolated new account persistence/SQL/authorization; (3) pure duplicate/planning engine; (4) review UI and two confirmations; (5) legacy migration, authentication integration, recovery and full release gate.

No production go until all phases, disposable hosted signed-token isolation tests, old/new-client fencing, interruption recovery, Windows → iPhone Safari → PWA and origin-specific offline acceptance pass. Keep package/UI at 0.8.3 until implementation is internally consistent. Do not output the final v0.9.0 release commit message for an incomplete intermediate tree.
