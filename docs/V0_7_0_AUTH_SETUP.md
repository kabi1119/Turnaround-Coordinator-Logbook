## Windows and Cloudflare setup

1. Create/select a dedicated Supabase project. Do not reuse an unrelated project's `public.profiles` table without reviewing its schema; this migration deliberately fails rather than dropping/replacing an existing table.
2. Obtain its HTTPS Project URL and **publishable key** (legacy `anon` JWT is also supported). Never use `service_role`, `sb_secret_`, SMTP passwords or admin credentials in frontend configuration.
3. In PowerShell at the repository root: `Copy-Item .env.example .env.local`. Fill `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`, then run `npm.cmd ci` and `npm.cmd run dev`. `.env.local` is ignored; do not paste credentials into source or commit it. Blank configuration intentionally disables sign-in while retaining Guest.
4. Supabase Authentication settings: disable **Allow new users to sign up**; enable Email for existing invited users. Also disable any anonymous/public registration provider. Frontend OTP always sends `shouldCreateUser: false`; server settings must enforce the policy independently. `supabase/config.toml` is a local configuration reference, **not evidence that hosted settings were applied**.
5. Set Email OTP to six digits, expiry 600 seconds; respect provider rate limits. Copy `supabase/templates/otp.html` into the **Magic Link / OTP** email template. It uses `{{ .Token }}`, not a link-only template. App resend cooldown is 60 seconds; server limits remain authoritative.
6. Configure production-capable custom SMTP, a verified sender/domain and appropriate sending/rate limits in Supabase. Default development email delivery is not production SMTP. Do not add SMTP secrets to Vite or Cloudflare static assets. No paid service was purchased or configured here.
7. Set Site URL to `https://app.tcologbook.workers.dev` (no trailing slash for the supplied invitation template). Add only exact trusted redirect URLs for intentional development/preview origins; avoid broad wildcards. Keep a stable long-term origin before accumulating records/passkeys. Preview and production may use separate Supabase projects; every origin has separate local records/vaults.
8. Copy `supabase/templates/invite.html` into the **Invite user** template. Its fragment `/#invite_token_hash={{ .TokenHash }}` is consumed and removed from history before verification with `verifyOtp({token_hash, type:'invite'})`; it is not sent in static hosting requests. No user-supplied redirect destination is followed. Default provider confirmation links can confirm the invitation at Supabase, but their implicit tokens are discarded by this app; sign in using Email OTP afterward.
9. Review/apply `supabase/migrations/202610200001_profiles.sql` once, using Supabase SQL Editor or your existing migration tooling. It creates only `profiles(id, created_at)`, with ownership RLS for SELECT/INSERT/UPDATE/DELETE and no anonymous grants. No operational tables exist. Do not weaken RLS to fix an onboarding error.
10. Use the reviewed v0.7.0 build before sending production invitations; an older deployed release will not handle the new fragment. For initial Windows testing, deliberately use a trusted local v0.7.0 Site URL/redirect origin instead, then restore the production values before publication. Invite the first beta user in Authentication → Users → Add user → Send invitation. Accept the invitation, then test Email OTP in the intended browser/PWA. Safari and an installed iPhone PWA may have separate authentication sessions and local storage; accepting in Safari does not sign the PWA in.
11. Configure the same two public variables in **Cloudflare Workers Builds build variables**, for each approved production/preview branch. These are build-time Vite values, not runtime Worker secrets. Rebuild after changing them. `main` remains the documented production branch; this session did not change remote branch settings or publish anything. Build/deploy commands remain the existing workflow.
12. Run `npm.cmd run check:release` before manual publication. Build generates a CSP allowing only same-origin assets plus the exact configured HTTPS Supabase origin for Auth/profile REST. The SDK's unused localhost default is replaced with a non-routable `.invalid` placeholder in the production transform, retaining the strict static URL gate. This transform deliberately fails if the pinned SDK constant changes and needs review. No wildcard connection permission, Worker backend or operational upload is added.

## Workspace and recovery boundaries

- Guest retains **the exact established schema-1 key** `tco-logbook-demo-v0.1`. Migration validates and records an ownership pointer (`tco-guest-owner-v1`), without copying/deleting/rewriting database bytes. It is repeatable; corrupt originals remain available to the existing Guest recovery UI. Choosing Guest is remembered separately. No existing record IDs, links, settings or backups change.
- First-time visitors see the welcome view before any operational workspace mounts. Returning Guest/legacy users go directly to Guest. A server-verified session opens a locked Account gate, never Guest records. Account profile resolution stores only the authenticated ID; login has no record import/upload.
- Account data is a separate schema-1 payload in `tco-account-vault-v1:<verified-user-id>`, initially **empty**, with its own settings. AES-256-GCM protects the entire payload using random 16-byte salt, random 12-byte IV for every write, PBKDF2-HMAC-SHA256 at 600,000 iterations and identity-bound additional authenticated data. Derivation count follows the [OWASP PBKDF2 guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Non-extractable keys and passphrases are never persisted. Namespace separation alone is not encryption.
- The local vault secret is separate from passwordless Email OTP. Use a long unique passphrase (12–1024 characters). Web Crypto requires HTTPS/localhost; if unavailable, Account fails closed and Guest remains available. Wrong secrets, damaged envelopes, wrong identity, unsupported versions and quota/stale-write failures never fall back to plaintext or reset a vault. Writes confirm only after encrypted persistence succeeds.
- Sign Out/Switch to Guest locks and unmounts the Account immediately, clears local Auth session storage, stops refresh and requests Supabase local-scope sign-out. Pending credential responses are fenced; new attempts wait for prior sign-out. Remote sign-out failure is reported separately. Other-tab session changes and expiry lock the active Account. Ordinary sign-out never deletes the encrypted vault.
- Explicit **Unlock saved local vault** requires the secret and labels the workspace **Session not verified**. This is local access, not renewed server authentication. Fresh online entry validates `getUser` and session expiry before showing data. Guest has no private profile access; network connectivity never means authentication or sync.
- Email addresses, OTPs and the minimal account profile are processed by Supabase for authentication; operational records stay local.
- The Auth SDK's refresh/session token has normal browser-SPA storage characteristics; it is not protected by the operational-data vault. Locking a vault does not protect an already unlocked session from malicious same-origin scripts, malware, browser extensions, weak passphrases or a compromised device. Encryption protects account records at rest; it is not an employer permission or an overall security certification.
- **No cloud record copy exists. Lost vault passphrases cannot be reset to decrypt records.** While unlocked, use Settings → Full local backup → Export Full Backup (JSON), save the actual downloaded file privately and verify it. Exports include archived/private fields and are **unencrypted**. Existing strict Preview/Replace Restore supports recovery into a deliberately selected unlocked workspace; it never merges or automatically transfers Guest records. Losing browser storage without a usable backup loses the local vault. No destructive reinstall/site-data clearing is recommended.
- The Service Worker remains a bounded static app-shell cache with unchanged update safety. Auth/profile responses, tokens, decrypted records, exports and arbitrary requests are not added to caches. Records are never uploaded by this release. `Device only` remains accurate in both workspace types. Guest-to-Account transfer, record sync, passkeys and encrypted cloud backup are deferred.

## Focused owner acceptance

1. Fresh desktop/390px browser: welcome, readable labels/focus, disabled gray Passkey, Guest usable offline. Reopen Guest without a repeated welcome. Existing v0.6.x records/settings/IDs/links must match the original backup.
2. Invite a test account, accept the invite, obtain/verify six-digit OTP. Test incorrect/expired codes, resend cooldown, rate limits and network interruption. An uninvited address must not create a user; check Dashboard user count as well as public UI. Do not use real operational data.
3. A first login starts empty; create a separate local vault, add a reviewed fictional Draft, reload/unlock and confirm persistence. Keep Guest untouched. Sign out/switch, verify Guest content restored, then verify Account B is empty and cannot see A's data. Expired/revoked sessions must lock; offline unlock must say Session not verified.
4. In a **disposable test Supabase database**, run `supabase/tests/profiles_rls.sql` as admin after migration. It uses synthetic users and rolls back. It asserts A/B isolation, denied foreign inserts/updates/deletes/ownership changes, and anonymous denial. Also test direct authenticated REST calls with test A/B tokens and no credentials from this repo. A SQL file/static assertion is not a live security pass. Do not run test fixtures in an operational project.
5. On desktop/phone, inspect Guest and Account headers, menu keyboard arrows/Escape, long email wrapping and Account Settings. Verify Handling/Duty/Journal save, failure/retry, Home summaries, unfinished navigation, reviewed JSON backup/restore, and offline Guest. On an actual iPhone, inspect Safari and Home Screen safe areas/keyboard separately; desktop emulation cannot certify them.

Live acceptance remains pending until an owner-configured project, email delivery, server signup restrictions/RLS and physical-device behavior are actually tested. No production-ready/security-certified claim is made.
